# 运营规范（Operating Charter）

> 这份文件是「我经营这个仓库」的底线和规矩。
> 任何一次提交、每一条 Issue 回复、每一个对外 PR，都要先过一遍这里。
> 它同时约束我自己，也约束任何帮我自动做事的 AI 助手。

---

## 一、自有仓库经营

1. **文档优先**：README 必须写清——项目用途、快速上手、环境依赖、部署文档、常见问题；有更新就同步更新，让外部人打开仓库就能看懂怎么用。
2. **代码提交规范**：提交信息（commit message）统一用 `feat:` / `docs:` / `fix:` / `chore:` 开头，清楚描述改动；重要功能走 PR 评审、留存记录，不一次性把大量未评审代码堆进 `main`。
3. **版本与标签管理**：稳定版本打 `tag`（如 `v0.1.0`），重大变更写进 `CHANGELOG.md`；区分开发分支 / 测试分支 / 主分支，`main` 始终保证可运行。
4. **Issue 维护**：收到外部 Issue 及时响应，分类标记（`bug` / `需求` / `疑问`），定期闭环；讨论保持专业、礼貌。
5. **仓库基础治理**：清理无效文件、密钥、配置明文、敏感业务数据；设好开源协议（`LICENSE`）；完善项目介绍与话题标签（Topics），提升曝光。
6. **持续维护**：定期迭代、修 bug、回复社区提问，把仓库当成对外技术品牌长期运营。

## 二、参与外部开源（给别人的仓库留言 / 改代码）

1. **留言（Issue / 评论）**：客观理性，描述问题带上**复现步骤 + 版本信息**；不发表争执、攻击性言论；提问前先搜现有 Issue，避免重复。
2. **修改他人代码（提 PR）**：
   - 先看对方仓库的 `CONTRIBUTING.md`，遵循其代码规范与分支规则；
   - 优先先开 Issue 与作者沟通想法，确认方向被接受，再动手写代码、提 PR，避免白做；
   - 修改范围克制：一次 PR 解决一个问题，不混杂无关改动，并附上改动说明；
   - **红线：严禁私自修改私有仓库、未授权项目代码；不提交侵犯版权、商业机密的代码。**

## 三、禁止事项（红线，绝不越界）

- 禁止在自有仓库和外部开源评论区发布广告、无关引流、争议言论；
- 禁止上传密钥、数据库信息、客户数据、内部涉密文档；
- 禁止未经授权 Fork 商业闭源项目、篡改版权声明；
- 禁止恶意给别的仓库提垃圾 PR、灌水评论。

---

## 自检清单（每次提交前过一遍）

- [ ] 提交信息是否符合 `feat:` / `docs:` / `fix:` / `chore:` 格式？
- [ ] 是否只改了该改的东西，没有夹带无关改动？
- [ ] 有没有把密钥 / 明文 / 敏感数据写进仓库？（`grep` 一遍）
- [ ] 文档是否同步更新了？
- [ ] 如果是给别人的 PR，是否先开过 Issue、看过对方 `CONTRIBUTING.md`？
